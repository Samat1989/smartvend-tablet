# Идея: ping платы перед каждым `payment_result` (esp-rt)

Статус: **идея, не реализовано.** Записано 2026-10-21 по итогам разбора возврата
(заказ `1196920261019171213fs8pig`, аппарат 11969, 19.10.2026).

## Проблема

В окне оплаты (60 с от QR, `supabase/functions/_shared/rt_payment.ts`) ping
платы идёт **один раз — до выдачи QR** (`create-payment`, `rtChannel.ping(3000)`).
Дальше каждые 3 с цикл проверяет только `ch.present()` — состояние Presence
в памяти, не запрос к плате — и зовёт `payment_result`.

Presence не мгновенный. При тихом обрыве (модем «в сети», данные не идут)
Realtime замечает пропажу по heartbeat: плата шлёт его раз в 25 с, таймаут
сервера — до ~60 с (значение для Supabase Realtime не проверено). Всё это
время `present() == true`, `payment_result` возвращает `code=1`, деньги
списываются, а `open` не доходит → `door_status = 'no_ack'`
(деньги взяты, дверь закрыта, ручной возврат).

## Предложение

В цикле `runPaymentWindow` вместо `ch.present()`:

1. Каждые **5 с** слать `ch.ping(2000–3000)` по WebSocket-каналу.
2. Есть `pong` → сразу `payment_result`.
3. Нет `pong` → тик пропускается, `payment_result` не зовём; следующий тик
   пробует снова.
4. **Финальный опрос прямо перед дедлайном** окна (при шаге 5 с последний
   обычный опрос может оказаться за ~5 с до конца, и поздняя оплата уйдёт
   в автовозврат).

Окно между «плата ответила» и «деньги списаны» сокращается с 25–60 с
до долей секунды. Остаётся промежуток `pong` → доставка `open` (секунды);
`open` повторяется до конца окна (не меньше 15 с после `code=1`).

## Почему не «3–4 попытки»

Это опрос раз в ~15 с: `code=1` замечается в среднем через 7 с (максимум 15),
оплата после последней попытки уходит в автовозврат, а окно слепоты платы
всё равно закрывает только ping перед каждой попыткой. Оптимум — шаг 5 с
(~12 попыток) + финальный опрос.

## Цена

- Задержка от оплаты до `open`: в среднем ~2–3 с, максимум ~5–6 с.
- Один потерянный `pong` (плохой GSM) пропускает тик; за окно ~10 попыток.
- Нагрузка Realtime: ~24 сообщения на заказ (12 тиков × ping+pong). Окно
  открывается на каждый заказ, не только на оплаченные. По базе: в октябре
  1375 заказов на аппаратах с `device_rt` за 21 день (~2000/мес) →
  порядка 50 000 сообщений в месяц.
- **Перед внедрением сверить** лимиты Supabase Realtime для тарифа проекта
  (Dashboard → Realtime → Settings: сообщений в секунду, подключений,
  квота сообщений в месяц). Точных цифр для проекта нет.

## Когда браться

Пока `no_ack` на аппаратах `esp-rt`: **1 случай на 2441 продажу** (~0,04%) —
исключение. Вернуться, если доля `door_status` не `opened` станет заметной
(например > 1% за неделю) или будут повторы на одном аппарате.

Как смотреть:

```sql
select m.id, m.name, s.door_status, count(*)
from sales s join micromarkets m on m.id = s.micromarket_id
join device_rt r on r.machid = m.id
where s.created_at > now() - interval '7 days'
group by 1, 2, 3 order by 1, 3;
```

Для `expired` (86 в октябре) ping не поможет различить причины: неоплата клиентом,
`code=3/4` от SmartVend и пропажа платы дают один и тот же статус. Причина — только
в логах `create-payment` (`[rt <machid> <orderid>]`): `board not in presence — not
polling` / `transaction expired/closed` / `window closed without payment`.
Логи в Supabase хранятся недолго — разбирать сразу.

## Связанные наблюдения

- `sales.door_status` имеет `default 'opened'`. Вендинги со спиралями
  (4552 продажи) идут не через `esp-rt`, и их `opened` ничего не значит —
  фильтр «`door_status` не `opened`» работает только для плат `esp-rt`.
  Для вендингов выдачу показывают `sales_items.dispensed` / `result_code`
  (как они заполняются — не проверено).
- Уведомление о выдаче LV (§6.3, weburlB, `status` 0/1) в коде не используется.
- Резервный серверный опрос в `create-payment` отключён «для теста» —
  см. комментарий `TEMPORARILY DISABLED`. Edge Function, оборвавшаяся посреди
  окна, оставляет заказ `pending` и ведёт к автовозврату.
