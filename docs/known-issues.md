## KI-1

### Планшет убивает себя примерно через 5 минут после потери связи с платой

**Статус:** ✅ исправлено в коде 2026-08-18, **в APK ещё не выпущено** — уедет
в парк вместе с релизом из KI-2.

**Симптом.** При потере связи с платой приложение показывает ошибку и примерно
через 5 минут само сворачивается. Приложение установлено как лаунчер
(`android.intent.category.HOME`), поэтому «свернулось» означает, что с экрана
пропадает вообще всё. Повторяется по кругу, пока плата не отвечает.

### Механизм

Это не сбой, а сработавшая лестница эскалации в
[`board_client.dart`](../apps/tablet/lib/board/board_client.dart) — портированная
из заводского приложения (`UsbUtil.isRestartApp` / `m933reboot`).

1. Watchdog тикает раз в 10 с. Плата молчит → `isHealthy` = false.
2. После 30 с непрерывного молчания (`_unhealthyGracePeriod`) счётчик
   `_reconnectAttempts` увеличивается и выполняется `forceReconnect()`.
   В `finally` сбрасывается `_unhealthySince`, поэтому **каждая следующая
   попытка снова ждёт свои 30 с** — итого 40–60 с на попытку.
3. На пятой попытке вызывается `KioskBridge.restartApp()`.

**5 попыток × 40–60 с ≈ 3,5–5 минут** — это и есть наблюдаемая задержка.

Нативная часть, `scheduleRelaunchAndKill()` в
[`MainActivity.kt`](../apps/tablet/android/app/src/main/kotlin/kz/smartvend/m102_tester/MainActivity.kt):
ставит `AlarmManager.set(RTC, now + 250 ms, …)` на запуск `MainActivity`, а через
80 мс делает `Process.killProcess()` + `exitProcess(0)`.

`_reconnectAttempts` обнуляется только при успешном обмене с платой. Если плата
отвалилась физически, обнуления не будет никогда → цикл вечный.

### Почему приложение не всегда возвращается

- `AlarmManager.set()` с обычным `RTC` — неточный будильник начиная с API 19,
  система вправе его отложить. `SCHEDULE_EXACT_ALARM` в манифесте не запрошен.
- Android 10+ блокирует запуск активити из фона. Будильник срабатывает уже
  после смерти процесса, и запуск может быть молча отброшен.
- Убивать процесс, который является лаунчером, опаснее вдвойне: если релонч не
  прошёл, подменить его на экране некому.

### Почему эскалация бессмысленна в этом сценарии

Её задача — расшевелить залипший драйвер CH340 **внутри своего процесса**. Она
не помогает, когда:

- плата обесточена, отключена или мертва — лечится только физически;
- транспорт нативный UART (`/dev/ttyS1`, как на BarysVend) — USB-драйвера нет
  вообще, отлипать нечему;
- платы нет по определению (микромаркет).

На протоколе LiYuTai `isHealthy` при подключении всегда true, поэтому watchdog
там не срабатывает: дефект касается только ветки M102 / M109E.

### Ловушка при чтении кода

Комментарий над лестницей эскалации утверждает:

> We only log — the app-restart and mainboard-reboot are factory-specific and
> need device-owner privileges we don't have here.

Это **неправда**: код ниже реально вызывает `KioskBridge.restartApp()`. Вызов
добавили позже, комментарий не поправили. Из-за него при чтении файла кажется,
что приложение себя не перезапускает.

### Принятое решение

**Самоубийство отключить полностью.** Счётчик и лог оставить для диагностики.

Киоск должен оставаться на экране с сообщением «нет связи с платой» и тихо
продолжать попытки переподключения. Оператору это понятнее исчезающего
приложения, и такое поведение не зависит от того, разрешит ли Android запуск
активити из фона.

### Что менять

- [x] Убрана ветка `_reconnectAttempts == 5 → KioskBridge.restartApp()`.
- [x] Убрана ветка `>= 10 → rebootDevice()` — перезагрузка всего планшета уводит
      киоск с экрана ровно так же и так же не чинит физическую неисправность.
- [x] Сообщения на порогах 2 / 5 / каждый 10-й оставлены в журнале платы,
      счётчик `_reconnectAttempts` работает как раньше.
- [x] Поправлен устаревший комментарий про «we only log» — теперь он правдив.
- [x] Убран ставший ненужным импорт `package:flutter/services.dart`
      (`PlatformException` использовался только в удалённой ветке).
- [ ] Проверить на живом автомате, что экран ошибки виден оператору и не
      перекрыт заставкой, пока связь не восстановлена.

`KioskBridge.restartApp()` / `rebootDevice()` и нативный
`scheduleRelaunchAndKill()` **оставлены на месте**, хотя вызовов у них больше
нет: это рабочий мост к нативной части на будущее. Если когда-нибудь понадобится
вернуть рестарт, сначала перевести будильник на `setExactAndAllowWhileIdle` +
`RTC_WAKEUP` и ограничить его одним разом за запуск.

### Как проверить после исправления

Отключить кабель платы на работающем автомате и оставить на 20+ минут:
приложение остаётся на экране, показывает ошибку связи, в журнале платы растёт
счётчик переподключений. Обратно подключить кабель — связь восстанавливается без
перезапуска приложения.

## KI-2

### Обновление планшета глохнет о релиз прошивки, лежащий сверху списка

**Статус:** 🟡 обходной путь применён на GitHub, фикс закоммичен, но **не
выпущен в APK**.

**Симптом.** После публикации релиза `pulse-v1.0.1+10001` планшеты перестали
видеть обновления и сообщали «у вас последняя версия», хотя `v1.1.25+11125`
лежал строкой ниже.

**Механизм.** `UpdateService.check()` отбирал релизы чёрным списком
(`tag.startsWith('relay-')`) и брал единственного кандидата через `firstWhere`.
Тег `pulse-…` под запрет не попадал, становился этим кандидатом, APK внутри не
содержал — и `check()` возвращал null.

**Обходной путь (применён 2026-08-18).** Релиз `pulse-v1.0.1+10001` помечен
`prerelease: true`. Старый код такие релизы пропускает, поэтому парк снова видит
`v1.1.25+11125`. OTA прошивки это не задело: ESP ищет обновления по списку
**тегов** и флаг `prerelease` не читает.

**Фикс.** Ветка `fix/tablet-update-tag-filter` — отбор по белому списку своего
формата тега (`^v?\d+\.\d+\.\d+`) вместо чёрного списка чужих, плюс перебор
кандидатов вместо отказа на первом. Живёт внутри APK, поэтому действует только
после выпуска новой версии планшета.

**Действующее ограничение.** Пока фикс не разошёлся по парку, **каждый релиз
прошивки (`relay-v*`, `pulse-v*`) публиковать с флагом prerelease**. Иначе он
снова встанет сверху списка обычным релизом и погасит обновления.
