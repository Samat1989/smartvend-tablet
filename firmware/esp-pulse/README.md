# esp-pulse — прошивка варианта платы с удержанием выхода

Копия [`../esp-relay`](../esp-relay/) для варианта платы, где замок управляется
**удержанием уровня на одном пине**, а не защёлкиванием бистабильного реле.

Всё остальное идентично esp-relay: MQTT-подписка на `vending/<uuid>/in`,
подтверждение заказа через `complete-order` **до** открытия, дедупликация по
`orderid` в NVS, provisioning-портал (SoftAP + captive DNS), GSM/Wi-Fi аплинк,
внешний watchdog, статусный светодиод, OTA с GitHub Releases.

## Отличие от esp-relay

| | esp-relay | esp-pulse |
|---|---|---|
| Выход | бистабильное реле: DIR **IO2** + импульс катушки **IO16** | один пин **IO2**, удерживается на всё время открытия |
| IO16 | импульс катушки | не используется |
| Открытие | защёлкнуть ON → ждать → защёлкнуть OFF | `HIGH` → ждать → `LOW` |
| Состояние после сброса | реле держит положение, поэтому на старте принудительно защёлкивается закрытым | пин отпускается сам; `lock_close()` на старте только сокращает окно |
| OTA-теги | `relay-v*`, ассет `relay-mart.bin` | `pulse-v*`, ассет `pulse-mart.bin` |
| Релиз | `release-relay.ps1` | `release-pulse.ps1` |

Код различия — три функции `lock_pins_init()` / `lock_open()` / `lock_close()`
в `main/main.c` (секция «Lock output»).

## Требование к схеме: IO2 активен HIGH

`LOCK_ACTIVE_LEVEL = 1` выбран не произвольно. GPIO2 — strapping-пин ESP32, и в
промежутке между сбросом и запуском `app_main` прошивка им не управляет: уровень
задаёт только то, что подпаяно на плате.

Поэтому **на затворе ключа (входе оптрона) обязательна подтяжка к земле**. Тогда
«прошивка ничего не делает» = «замок закрыт» на всём протяжении сброса,
бутлоадера и OTA.

Если на конкретной плате выходной каскад окажется инвертирующим (активный LOW) —
это надо чинить схемой, а не менять `LOCK_ACTIVE_LEVEL`: с активным LOW замок
будет коротко открываться при каждой перезагрузке.

Перед первой заливкой проверьте, что **IO2 действительно выведен на выходной
каскад** этого варианта платы, а не остался на драйвере бистабильного реле — в
последнем случае удержание DIR без импульса на IO16 не сделает ничего. Прозвонить
удобно прошивкой [`../relay-test`](../relay-test/README.md): `g 2 1` / `g 2 0`.

Пины GSM-модема (25/26 + питание 5), внешнего WD (32) и светодиода (33)
унаследованы от базовой платы — если вариант отличается, сверьте по своей схеме.

## Настройка

Время удержания задаётся в сервисном портале полем «Время удержания замка, сек»
(NVS-ключ `opensec`, 1…600, по умолчанию 20) — та же семантика, что и время
включения реле в esp-relay.

Вход в портал: в течение 4 с после подачи питания нажать кнопку BOOT более
3 раз. Дальше — Wi-Fi `SmartVend-Setup-XXXX`, страница `http://192.168.4.1`.

### Выход из сервисного режима по таймеру

Портал — это открытая точка доступа без пароля, поэтому автомат, забытый в
сервисном режиме, может перенастроить кто угодно в радиусе Wi-Fi. **После 3 минут
без единого запроса к странице устройство перезагружается в рабочий режим**
(`PORTAL_TIMEOUT_MS`).

Таймаут именно по бездействию, а не абсолютный: заполнение формы плюс 30–60 с
на подъём GSM-модема легко перекрывают три минуты, и обрывать монтажника на
середине настройки было бы хуже, чем риск, который мы закрываем. Любой запрос к
порталу сбрасывает счётчик, а на время сохранения настроек он вообще
замораживается — эти ветки перезагружаются сами.

**Таймер не взводится на непривязанном устройстве** (свежая плата, в NVS пусто).
Возвращаться там некуда: перезагрузка снова привела бы в портал, то есть вышел бы
цикл ребутов с той же поднятой AP. Новая плата ждёт монтажника сколько нужно —
это и единственный вход в неё, если не попадать в 4-секундное окно кнопки BOOT
после подачи питания.

## Сборка и прошивка

```bash
# в окружении ESP-IDF (export.ps1 / get_idf)
cd firmware/esp-pulse
idf.py set-target esp32
idf.py -p COM9 build flash monitor
```

`build/`, `managed_components/` и `sdkconfig` генерируются — в репозитории лежат
только исходники, `sdkconfig.defaults` и `partitions.csv` (OTA-разметка на 4 МБ:
два слота по ~1.9 МБ).

## Релиз

```powershell
.\release-pulse.ps1 "Что изменилось"
```

Скрипт бампает `FW_VERSION_NAME`/`FW_VERSION_CODE` в `main/main.c`, собирает,
коммитит, ставит тег `pulse-vX.Y.Z+CODE` и заливает `pulse-mart.bin` в GitHub
Release.

**Три потока обновлений живут в одном репозитории** и разделены только префиксом
тега и именем ассета: планшет (`v*`), esp-relay (`relay-v*`), esp-pulse
(`pulse-v*`). Не переиспользуйте чужой префикс — плата с esp-pulse, подхватившая
relay-сборку, останется с мёртвым выходом замка.

## Что проверить на стенде

1. Портал → сохранить время удержания, перезагрузка, в логе
   `Pulse Mart System Started (LOCK IO2 active HIGH, hold 20s)`.
2. Публикация `{"msg":"Processed order","code":1,"orderid":"<новый>"}` в
   `vending/<uuid>/in` → в логе `🔓 LOCK OPEN`, замок открыт заданное время,
   затем `🔒 LOCK CLOSED`.
3. Повторная публикация того же `orderid` → `Duplicate order ID detected`,
   замок не открывается.
4. Нет связи с Supabase → `order ... NOT confirmed by server — lock stays CLOSED`,
   замок не открывается (деньги не забираются без открытия).
5. RST в момент удержания → пин отпускается, замок закрывается.
6. Вход в портал на привязанном устройстве, ничего не трогать 3 минуты →
   `portal idle 180 s — rebooting into normal mode`, автомат вернулся в работу.
7. Вход в портал, каждые пару минут обновлять страницу → перезагрузки нет.
