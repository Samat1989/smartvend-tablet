# Системные полосы и автозапуск на планшетах SHENGMA

Про то, кто на самом деле решает, будет ли внизу экрана кнопка «Назад», и
почему приложение больше не HOME.

Всё ниже проверено 25.08.2026 на двух планшетах: заводском китайском автомате
и нашем `kz.smartvend.m102_tester`. Разобрано из заводского APK
`com.shengma.shouhj.sy.world` 03.78.3 и из `/system/framework/services.jar`
самой прошивки.

## О каком железе речь

```
ro.product.model       sp9832e_1h10_go2g      (Unisoc SC9832E, Android 13 Go)
ro.build.display.id    rc800_XX16_SHENGMA_general_AndroidT_user_*
```

Прошивку внутри приложения называют **RY** / 锐翊 («Жуйи»). Тип платы лежит в
настройках заводского приложения как `FLAG_SYSTEM=RY`, и от него зависит,
какой из вендорских API оно дёргает. Кроме RY в APK лежат ветки под ZTL, LYZK,
DING, KIAYO и Yiputeng — на нашем железе они мертвы, приёмников нет.

## Полосы принадлежат прошивке, а не приложению

Две property, которые читает `services.jar` при инициализации дисплея:

```
persist.sys.navbar.disabled       = true → навбар вообще не создаётся
persist.sys.statusbar.disabled    = true → статусбар не отображается
```

Пока `navbar.disabled=false`, окно навбара создаёт WindowManager, и перебить
это **нельзя ничем на стороне приложения**: ни `WindowInsetsController.hide()`,
ни sticky immersive, ни Device Owner с lock task. Именно на это ушло много
времени: приложение делало всё правильно, а полоса оставалась.

Статусбар ведёт себя коварнее. В lock task с `setLockTaskFeatures(0)` система
гасит в нём часы и иконки (`mDisabled1=0x7a60000`, `mDisabled2=0x1f`, включая
`DISABLE2_NOTIFICATION_SHADE`), но само окно остаётся видимым и съедает инсет
36 px. На экране это выглядит как пустая серая полоса сверху — не шторка, а её
труп. Шторка при этом уже не открывается: проверяется командой
`adb shell cmd statusbar expand-notifications`, фокус остаётся на приложении.

### Ключевая ловушка

**Обе property применяются только при следующей загрузке.** `setprop` или
broadcast на работающей системе не меняют ничего. Проверять эффект без
`adb reboot` бессмысленно — именно из-за этого механизм долго выглядел
нерабочим.

## Четыре команды прошивки

Заводское приложение управляет всем этим через broadcast'ы. Они целиком
выписаны из класса `ApiSmRySystem`:

```
android.intent.action.shouhj.STATUSBAR_ON     обе property → false
android.intent.action.shouhj.STATUSBAR_OFF    обе property → true
android.intent.action.shouhj.REBOOT           перезагрузка
android.intent.action.shouhj.SHUTDOWN         выключение
```

Приёмников-приложений у них нет — `cmd package query-receivers` отвечает
`No receivers found`. Их обрабатывает system_server. Практический вывод:
**отправить их может любое приложение** — без разрешений, без root, без Device
Owner. Заводскому приложению разрешение `REBOOT` система не выдала
(`granted=false`), и оно ему не нужно.

С командной строки:

```bash
adb shell am broadcast -a android.intent.action.shouhj.STATUSBAR_OFF
adb reboot
```

или напрямую, минуя прошивочный слой:

```bash
adb shell setprop persist.sys.navbar.disabled true
adb shell setprop persist.sys.statusbar.disabled true
adb reboot
```

Оба пропа попадают под SELinux-контекст `system_prop`. SELinux на устройстве
`Enforcing`, но shell (uid 2000) писать их может — root не нужен.

## Как заводское приложение стартует после включения

Оно **не лаунчер**. HOME на заводском планшете — стоковый
`com.android.launcher3/.Launcher3QuickStepGo`. Приложение поднимается поверх
него через `BOOT_COMPLETED`. Живой лог загрузки:

```
15:21:19.379  START {cat=[HOME] cmp=com.android.launcher3/.Launcher3QuickStepGo} from uid 0
15:21:21.114  фокус: FallbackHome → launcher3
15:21:22.969  Start proc com.shengma.shouhj.sy.world for broadcast BootReceiver
15:21:25.374  START {flg=0x10000000 cmp=.../ShanpingYeActivity} from uid 10131
15:21:25.376  W/ActivityTaskManager: Background activity start for
              com.shengma.shouhj.sy.world allowed because
              SYSTEM_ALERT_WINDOW permission is granted.
```

Обычный `startActivity` из ресивера — это background activity start, который
Android 10+ должен запретить. Пропускает его исключение по
`SYSTEM_ALERT_WINDOW`.

### Почему хватает одного объявления в манифесте

`appops get com.shengma.shouhj.sy.world SYSTEM_ALERT_WINDOW` показывает
`default; rejectTime=...`, то есть галочку «Поверх других приложений» никто
не включал. Но у этого разрешения флаг защиты `appop`: **сама permission
выдаётся при установке**, а appop лишь решает, можно ли реально рисовать окно.
Проверка во фреймворке устроена так:

```java
mode = noteOpNoThrow(OP_SYSTEM_ALERT_WINDOW, ...);   // MODE_DEFAULT, пишет rejectTime
if (mode == MODE_DEFAULT) {
    return checkPermission(SYSTEM_ALERT_WINDOW, pid, uid) == GRANTED;   // true
}
```

Тот самый `rejectTime` — след этой проверки в момент автозапуска. Никаких
действий оператора не требуется.

**Ограничение:** в Android 14 исключение урезали, одной выданной permission
там уже мало. На планшетах новее (K80) автозапуск этим путём не поедет.

## Что из этого сделано у нас

### Приложение убрано из HOME

Раньше `configureDeviceOwnerKiosk()` прописывал
`addPersistentPreferredActivity(HOME)`, и планшет загружался сразу в киоск, без
мигания лаунчера. Красивее, но:

* поведение расходилось с заводским автоматом, на который мы ориентируемся;
* планшет, у которого киоск не стартует, становился недостижим без кабеля.

Теперь вместо этого вызывается
`clearPackagePersistentPreferredActivities(admin, packageName)`.
**Просто перестать прописывать было недостаточно** — привязка, выданная
прошлой сборкой, живёт в системе и переживает переустановку приложения. Её
нужно снимать явно.

`CATEGORY_HOME` убран и из манифеста. Возвращать эти две вещи имеет смысл
только вместе — по отдельности они бесполезны.

Цена решения честная: **~6 секунд стокового лаунчера** на экране после
загрузки, ровно как на заводском автомате.

### Полосы гасятся при каждом старте

`MainActivity.onCreate` шлёт `STATUSBAR_OFF` безусловно — так же, как заводское
приложение, у которого в логе на каждом запуске:

```
Android系统--setSystemBar：false
锐翊主板--隐藏导航栏状态栏
```

Это не паранойя, а механизм: именно он делает сервисный пункт «Показать
навбар» самоотменяющимся.

### «Показать навбар» в сервисном меню

`KioskBridge.showNavBarAndReboot()` → `STATUSBAR_ON`, пауза 700 мс, ребут.

Пауза нужна: property пишет system_server, пока обрабатывает broadcast, и
ребут в тот же момент может её обогнать.

Дальше цикл замыкается сам:

| шаг | что происходит | полосы |
|---|---|---|
| 1 | оператор жмёт «Показать навбар» → `STATUSBAR_ON` → ребут | появились |
| 2 | приложение стартует → `STATUSBAR_OFF` (property снова `true`) | ещё видны |
| 3 | оператор доделал дела, перезагрузил | исчезли |

Возвращаться в сервисное меню и что-то выключать не нужно. Так же ведёт себя
заводская настройка — это не совпадение, а копия.

### Закрепление экрана — только с device owner

У Android два режима lock task, и это не две ступени одного и того же:

| режим | когда | что делает |
|---|---|---|
| `LOCKED` | есть device owner | тихо, без диалога; с `setLockTaskFeatures(0)` забирает и шторку |
| `PINNED` | все остальные | показывает «Приложение закреплено — чтобы открепить, нажмите и удерживайте «Назад» и «Обзор»» и **возвращает навбар**, потому что эти две кнопки теперь официальный выход |

То есть на непровижиненном планшете закрепление отменяет то, ради чего всё
затевалось: возвращает полосу, убранную прошивкой, и вдобавок объясняет
покупателю, как выйти.

Поэтому `tryEnterLockTask()` теперь первым делом проверяет `isDeviceOwner()` и
без прав не делает ничего. Если приложение почему-то уже оказалось в `PINNED`
— вызывает `stopLockTask()` и выходит: сообщение и навбар уходят вместе с ним.

Ничего не теряется. Без device owner защита держится на том, что полос нет на
уровне фреймворка, а это замок надёжнее закрепления: у закрепления есть
документированный выход двумя кнопками, а у отсутствующего навбара выхода нет
вовсе.

### Watchdog удалён

Вместе с закреплением ушёл и сторож: тик раз в секунду, который вытаскивал
приложение обратно на передний план, пока оно не на экране. Он задумывался как
киоск для планшетов без device owner.

Причина та же. Когда полос нет на уровне прошивки, у покупателя нет ни Home, ни
Overview, ни Back — выходить нечем, и сторожу нечего отыгрывать. Зато он делал
планшет необслуживаемым: оператор, добравшийся до настроек, вылетал оттуда
через пару секунд, и вылечить это можно было только `am force-stop` по кабелю.

Заодно исчез `ensureOverlayPermission()` — заход в системный экран «Поверх
других приложений» при первом запуске. Он существовал ровно затем, чтобы тики
сторожа проходили. Разрешение `SYSTEM_ALERT_WINDOW` в манифесте **остаётся** —
это то, что даёт автозапуск через `BootReceiver`, — но галочку у оператора
больше никто не просит: нужна permission, а не app-op.

### Перезагрузка с деградацией

`rebootTablet()` пробует по очереди:

1. `DevicePolicyManager.reboot()` — чисто, синхронно, нужен Device Owner
2. broadcast `shouhj.REBOOT` — без разрешений, единственный путь на
   непровижиненном планшете
3. если не вышло ни то ни другое — вызывающий откатывается к
   `restartApp()` и перезапускает хотя бы процесс

В «Системных настройках» на это заведена отдельная кнопка «Перезагрузить» —
обычный ребут, без возни с property, для случаев «плата замолчала» или
«оператор уезжает и хочет оставить аппарат свежезагруженным».

## Определение прошивки

Приложение ставится не только на заводские автоматы, поэтому вендорские пути
включаются не всегда, а по факту. Проверяется **наличие самой property**, а не
название сборки:

```kotlin
ProcessBuilder("/system/bin/getprop", "persist.sys.navbar.disabled")
```

`android.os.SystemProperties` для нас скрытый API, а `getprop` — обычный
исполняемый файл, доступный любому приложению. Неопределённая property
возвращает пустую строку — однозначный признак, без исключений и догадок.

Почему не `Build.DISPLAY.contains("SHENGMA")`: проверять надо то, от чего мы
зависим — фреймворк, который читает эту property при инициализации дисплея.
Перемаркированная сборка той же прошивки ответит, а посторонний планшет с
похожим названием — нет. На только что сброшенном планшете property тоже
определена (читается `false`, не пусто), так что проба работает до первой
записи.

Результат кэшируется на время жизни активности — ROM под работающим
приложением не меняется — и уезжает в Dart методом `firmwareCapabilities`:

```
vendorBars    прошивка распоряжается полосами
vendorReboot  прошивка перезагружает по broadcast'у
deviceOwner   выданы права владельца устройства
firmware      Build.DISPLAY, для диагностики
```

Экран «Системные настройки» (сервисный режим → плитка с шестерёнкой) по этим
флагам **гасит плитки** и подписывает причину, вместо того чтобы предлагать
кнопку, которая молча ничего не делает:

| плитка | активна когда | подпись, если нет |
|---|---|---|
| Показать навбар | `vendorBars` | «только на заводской прошивке SHENGMA» |
| Перезагрузить | `deviceOwner` или `vendorReboot` | «нужны права владельца устройства» |

Это не только косметика. `sendBroadcast` успешен независимо от того, слушает
его кто-нибудь или нет, поэтому раньше кнопка «Перезагрузить» на чужом
планшете отчиталась бы об успехе и не сделала ничего. Теперь `rebootTablet()`
без прошивки и без owner честно возвращает `false`.

## Что будет на планшете другого поставщика

| | без owner | с owner |
|---|---|---|
| вендорские broadcast'ы | не отправляются, плитки погашены | то же |
| полосы | прячет только immersive — свайп от края возвращает | то же + `LOCKED` глушит шторку, Home и Overview |
| закрепление экрана | не вызывается | `LOCKED`, тихо |
| возврат на передний план | никто не возвращает | не нужен |
| автозапуск | `BootReceiver` + `SYSTEM_ALERT_WINDOW`, Android 10–13 | так же |

Вывод: **на чужом железе device owner обязателен**. Без него киоска
фактически нет — покупатель свайпает от края, получает навбар и уходит, и
ничто его не вернёт. На заводских планшетах это безопасно только потому, что
свайпать там нечего.

Универсальной adb-команды, убирающей навбар как на SHENGMA, не существует:
`persist.sys.navbar.disabled` — собственность этой прошивки, а общий
`settings put global policy_control immersive.navigation=*` перестал работать
с Android 12. На чужом планшете полосы прячет immersive приложения, и это
слабее — свайпом их видно.

## Проверка на живом планшете

```bash
adb shell getprop persist.sys.navbar.disabled       # ждём true
adb shell getprop persist.sys.statusbar.disabled    # ждём true
adb shell "dumpsys window windows | grep -c NavigationBar"          # ждём 0
adb shell "dumpsys window | grep 'ITYPE_STATUS_BAR frame'"          # ждём visible=false
adb shell "dumpsys activity activities | grep mLockTaskModeState"   # ждём LOCKED
adb logcat -d | grep "Background activity start"                    # причина автозапуска
```

Выход в Android, когда полос нет и кнопки Home не существует:

```bash
adb shell am start -a android.intent.action.MAIN -c android.intent.category.HOME
```

## Что осталось от заводского аппарата не скопированным

Ежедневная профилактическая перезагрузка. У завода этим занимается
`RebootService`: время генерируется **случайно и один раз на устройство**

```java
String str = "0" + getRandom(5, 3) + ":" + getRandom(50, 10);   // 03:10 … 05:50
```

и запоминается в настройках (у разобранного экземпляра вышло `04:20`). Раз в
50 секунд сервис сверяет часы и дёргает `reboot(9)`. Приём стоит перенять,
когда дойдут руки: парк из сотни автоматов иначе придёт на сервер одной
волной. Триггеры перезагрузки у них, судя по коду: команда с сервера, 5 минут
без сети, потеря связи с платой, сбой串口-клиента, смена SN платы.
